# Signup, confirmation, social sign-in and photo fixes

Continues `feature/szocial-supabase-auth-storage` and updates draft PR #1. No SQL, schema, migration, hosted account, Storage object or payment record was changed for this task. The existing eight migrations remain applied; do not reapply them.

## Root causes and changes

**Normal signup:** the API always reported confirmation as required without inspecting the session, while the store converted an accepted pending signup into `false`. Both signup screens had clickable handlers without synchronous submission guards. This left users on the form and permitted additional signup/email requests.

The API now distinguishes confirmation-required, authenticated, rejected, rate-limited and uncertain outcomes. Resident and business forms immediately show `Creating account...`, disable submission and synchronously guard clicks, Enter and concurrent handlers. Accepted signup navigates to `/check-email` or authenticated onboarding. Successful and uncertain requests cannot be automatically submitted again. Backend duplicates for the same pending email return the existing pending state without calling Supabase signup again.

`/check-email` displays an accepted-request explanation, a masked email address, inbox/spam instructions, the correct login destination, and a guarded resend control. It does not claim delivery. Resend requires an accepted signup stored in an encrypted HttpOnly cookie, uses a 120-second minimum cooldown, preserves longer provider `Retry-After` values, and returns HTTP 429 properly. A bounded per-process email guard supplements the encrypted cooldown; Supabase's project-wide limits remain authoritative across instances. It is not a distributed rate-limit datastore. No rate limits or email-verification settings were disabled or increased.

Pending state contains only encrypted email, intent and timing information, expires after 24 hours, and is cleared after verified authentication. Passwords and raw photos never enter this cookie, URLs, local/session storage or user metadata. Production requires a stable server-only `AUTH_RATE_LIMIT_SECRET` or the existing `SUPABASE_SECRET_KEY`; development can use a process-lifetime random key. All production instances must share the same stable key.

**Callbacks and onboarding:** code and token-hash callbacks now verify the session and query database onboarding state/roles. New users complete onboarding; existing users reach their appropriate dashboard. Business intent only chooses setup; it grants no role. Failed/expired/cancelled callbacks use `/auth/error` with useful recovery links. Recovery links retain `/reset-password`. Email login and middleware also keep incomplete profiles in onboarding. Callbacks do not insert duplicate profiles or businesses.

**Social sign-in:** the reported `Unsupported provider: provider is not enabled` error indicates Google was disabled when the user tested it. This task cannot independently inspect the current hosted provider configuration: direct Auth API access is still denied by the running cloud network policy, no management token is available, and the exposed MCP tools do not include Auth/provider/SMTP configuration. Facebook status, client credentials, Site URL, redirects and SMTP are therefore unverified, not assumed enabled.

The app reads only public provider flags from `/auth/v1/settings` through `/api/auth/providers`. Disabled and unknown states prevent a redirect and explain email alternatives on all four authentication screens. Settings are cached for 30 seconds; use Check again after that interval when changing dashboard settings. `/api/auth/oauth` rechecks availability, builds a server-side PKCE redirect, validates the destination and explicitly requests Facebook's `email` permission. The app never receives provider secrets.

**Photo crop:** the component used image-load events to initialize geometry while a passive effect reset the same state. It also replaced the loading image with a different rendered image subtree. Cached/fast loads could be reset without a subsequent load event, leaving geometry unset, the circles blank and controls disabled.

The shared cropper now starts a separate cancellable image decode from its source/open effect, accepts only valid natural dimensions, and ignores stale loads. Rendering no longer initializes loading state. It has loading/error feedback and a decode timeout, bounded dimensions, synchronous apply protection, pointer/keyboard movement, zoom/reset and validated 512×512 JPEG canvas output. FileReader errors, unsupported/empty/corrupt/oversized files and stale selections have explicit handling. No object URLs are created, so none require revocation.

Resident signup and profile editing use the fixed component; onboarding now offers the same cropper. Signup profile details/photo are held only in React memory. They can carry through same-document navigation; an email callback/reload may clear that memory. Users can reselect the photo and complete optional details during authenticated onboarding. Uploads then use the existing ownership-checked Storage API. Business galleries and post attachments retain their existing behavior.

## Remaining external configuration

Only use the dedicated **Szocial** project. Profolio must remain untouched. Copy the **provider callback URL shown by Szocial's provider panel**; do not substitute your Next.js callback or another project's URL.

1. **Supabase URLs:** in Authentication → URL Configuration, use `http://localhost:3000` as the Site URL for the current local test setup. Add `http://localhost:3000/**` to additional redirects for local development. Localhost and `127.0.0.1` are different origins; use localhost consistently. Before deployment, use the real application origin and explicit production callback/confirmation/recovery redirects. Do not invent a production domain or use the development wildcard for production.
2. **Google:** in Google Cloud → Google Auth Platform, configure Branding, Audience and Data Access. Add intended accounts as test users while the app is in Testing. Enable only `openid`, `userinfo.email` and `userinfo.profile`. Create an OAuth **Web application** client in Clients/Credentials. Set the app's JavaScript origin to `http://localhost:3000` for local testing. Set its authorized redirect URI to the exact **Supabase provider callback URL** from the Szocial Google panel (shape: `https://<Szocial-project-ref>.supabase.co/auth/v1/callback`). Enter Client ID and Client Secret only in Szocial Authentication → Sign In / Providers → Google, enable Google and save. Verify new/existing resident and business sign-ins through actual consent. App provider flags being enabled do not prove the credentials or consent screen work.
3. **Facebook:** create/configure a Meta developer app with Facebook Login. Enable web/client OAuth login and register the exact **Szocial Supabase callback** as a Valid OAuth Redirect URI. Configure the required `email` permission and default `public_profile`. Enter App ID and App Secret only in Szocial's Facebook provider panel, enable and save. While the Meta app is in Development mode, assign developer/tester/test-user roles and accept the invitations before testing; arbitrary Facebook accounts will not necessarily be allowed. Confirm the test account has an email available to Facebook and grants the email permission. Before public release, complete Meta's required permission/access review, privacy policy and data-deletion configuration using real URLs. No Meta app settings were accessible to this task.
4. **Email/SMTP:** inspect Authentication → Email → SMTP Settings (Custom SMTP) and the current Auth rate-limit settings. The actual transport and quotas could not be inspected here. Supabase's built-in mail service has restricted recipients and low quotas and is unsuitable for repeated/production delivery testing. If needed, configure a trusted SMTP service with a verified sender/domain, provider host/port/TLS credentials, sender address and `Szocial` sender name. Store credentials only in the dashboard/secret manager. Complete sender DNS verification (SPF/DKIM and the provider's recommended DMARC setup). Keep email confirmation enabled. Test minimally using dedicated test accounts; use local Mailpit/Inbucket or mocked delivery for repeatable automation.
5. **Confirmation templates:** the default Supabase confirmation link should redirect through `/auth/callback?next=...` generated by this app. If using token-hash templates instead, link to `/auth/confirm` with `token_hash`, a supported `type` (`email`/`signup`, or `recovery` for resets), and preserve `next` or `redirect_to` from the app's generated redirect. Both callback forms are tested; avoid mixing a PKCE code with a token-hash-only link or dropping business intent.
6. **Server/runtime configuration:** make the existing Szocial public URL/key and server-only Storage secret available to the local/deployed app. Use a stable `AUTH_RATE_LIMIT_SECRET` (or the server Supabase secret fallback) across production instances for encrypted confirmation state. This running cloud task still lacks the newly configured server secret/network policy, so it could not validate hosted transfers or settings. Never paste credentials into chat or commit `.env.local`.
